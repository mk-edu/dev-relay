# dev-relay: dev

設計・実装・レビューを別々の担当に分けて開発タスクを進める。同じモデルが書いたものを同じモデルが確かめると、同じ前提と同じ見落としが残る。担当を分けるのはそれを避けるため。

| 担当 | 誰が | 理由 |
|---|---|---|
| 設計、採否の判断、ユーザーへの報告 | メインセッション | ユーザーの要望と会話の経緯を持っているのはここだけ |
| 設計レビュー、コードレビュー | レビュアー（別ベンダーのモデル。Codex CLI、Cursor CLI 経由のモデル、どちらも無ければ Claude の別モデル） | 別ベンダーのモデルなので、見落としの傾向が重ならない。Claude で代替したときは独立性が落ちるので、報告に書く |
| 実装、テスト、指摘の修正 | 実装者（Herdr の中で動いているときは hc の子エージェント、それ以外は Agent ツールの `dev-relay:implementer`。難所は `dev-relay:implementer-hard` に当たるモデル） | 設計書に判断が書いてあれば、実装で迷う箇所が無い。設計書に書き漏らした前提が、実装者の質問として表に出る |

メインセッションのモデルはユーザーが選ぶ。設計と採否の判断に向かない小さいモデルで動いていると気づいたら、始める前に一言伝える（止めはしない）。

以下、このスキルのディレクトリ（この SKILL.md がある場所）を `<skill-dir>` と書く。

## 最初にやること

1. **目的を自分の言葉で言い直す。** ユーザーが何を解決したいのか、変更が何を満たせばよいのかを1〜3文で書く。この文章はそのままレビュアーに渡す「目的」になり、レビューの指摘は目的に反する動作に絞られる。目的がはっきりしないときは、ここでユーザーに聞く。
2. **モードを提案し、ユーザーに選んでもらう。**

   | モード | 使う場面 | 工程 |
   |---|---|---|
   | `full` | 複数ファイルにまたがる機能追加・変更・リファクタリング | 設計書 → 設計レビュー → 実装 → コードレビュー |
   | `bugfix` | 不具合の修正 | 再現 → 原因メモ → 失敗するテスト → 修正 → コードレビュー |
   | `review` | 小さい修正、すでにある差分 | コードレビューだけ |

   `full` は設計書1本、レビュアー2回、実装者1体以上を使う。変更の大きさに見合わないときは、小さいモードを提案する。
3. **実行環境を確かめる。** `dev-relay doctor` を実行し、`references/runtime.md` と `references/reviewers.md` を読む。Herdr の有無（レビューと実装者の起動のしかたが決まる）、選ばれるレビュアー、worktree を使うかを決める。Herdr（hc）が無くても、Codex も Cursor CLI も無くても進められる。

   送り先（コードを送ってよい提供元）を尋ねるのは次の2つの場合だけで、どちらも `vendor-not-allowed` だけが理由で飛ばされた候補があるときに限る（道具が入っていないなら、尋ねても選べるものが無い）。
   - `repo.vendors.source=unset`: `setup` がまだなので、`/dev-relay:setup` の手順4（利用者の既定を選ぶ）をその場で行う。
   - `repo.vendors.source=ask` で `git.repo=yes`: このリポジトリで使ってよい送り先を1度尋ね、答えを `dev-relay config vendors --repo <一覧|none>` で書く。断られたときも `none` を書くので、同じリポジトリで2度は尋ねない。git リポジトリの外で `ask` のときは、答えを保存する場所が無いので、尋ねずに Claude のレビュアーで進める。
4. **作業のフォルダを作る。** `dev-relay work dir <topic>` を実行する（`<topic>` は英小文字・数字・ハイフンの短い名前）。この作業で作るファイル（設計書、レビューの結果、実装者への指示と報告、テストのログ）は、すべてこのフォルダに置く。出力の `work.dir`、`work.review`、`work.impl`、`work.logs` が置き場所で、git に無視される。

   | 置くもの | 場所 |
   |---|---|
   | 設計書（bugfix は原因メモ） | `<work.dir>/design.md`（bugfix は `cause.md`） |
   | レビューの結果 | `<work.review>/design-1.md`、`code-1.md`、追加のレビュアーは `code-1-extra.md`。再レビューは `-2` |
   | 実装者への指示と報告 | `<work.impl>/brief.md`（組に分けたら `brief-a.md`）、`report-a.md` |
   | テストなどの出力 | `<work.logs>/` |

   前の作業のフォルダが `.dev-relay/` に残っていて、その変更がコミット済みなら、`dev-relay work done <前の topic>` で `done/` に移してから始める（手順の7）。

## full モード

### 1. 設計書を書く

会話の中だけにある設計は、レビューにも実装の委譲にも出せない。Markdown ファイルに書き出す。置き場所は、リポジトリに `docs/design/` や `docs/adr/` のような慣習があればそこ、無ければ `<work.dir>/design.md`。

含める節: **目的 / 背景と制約 / 採用する方針 / 検討して捨てた代替案 / 影響範囲 / データの形（主要な型と状態） / 変更するファイルと関数 / テスト方針 / 未決事項**

- この設計書はそのまま実装者への指示書になる。「実装者が設計書だけを読んで、迷わず書けるか」を基準に粒度を決める。
- 書く前に、今回の変更で消せるものが無いか、より小さい変更で目的を満たせないかを検討する。
- ロジックより先にデータの形を決める。分岐が多い、同じ前提を複数の場所で繰り返す、といった設計は、状態や型の持ち方で解消できることが多い。
- 変更するファイルを、互いに重ならない組に分けられるなら、「変更するファイルと関数」を組ごとに分けて書く。実装者を同時に動かせる（手順4）。組の間の取り決め（コマンドの引数、関数の名前、ファイルの形式）は、設計書の中で決めておく。
- 未決事項は隠さずに書く。書いておくと、その論点への代替案や判断材料が指摘として返ってくる。

### 2. レビュアーに設計レビューを頼む

```bash
dev-relay review design <設計書> --out <結果ファイル>
# 観点を足したいとき: --focus "並行性とデータ整合性"
```

起動のしかた（Herdr の端末で動かす、バックグラウンドで動かす、終了コード 3 が返ったとき）は `references/runtime.md` の2節。レビュアーは設計書に加えてリポジトリを読み取り専用で参照するので、既存コードとの整合もレビューの対象になる。

依頼の文面はスクリプトが固定のテンプレートから作る。自分の結論を添えて追認を求めると、独立した視点にならないため。

### 3. 採否を決めて設計書を直す

`references/triage.md` に従い、指摘を1件ずつ採用・不採用・ユーザー判断に分ける。

- 指摘の根拠に挙がったコードの場所は、自分で開いて確かめる。
- 「実行すれば決まること」は、ユーザーに尋ねる前に実行して確かめる。ユーザーに聞くのは、実行しても決まらない好みや方針の選択だけにする。
- 採用した指摘を設計書に反映し、結果をユーザーに報告する。異論が無ければ実装に進む。

### 4. 実装を委譲する

`references/implementer-prompt.md` を埋めて、実装者に渡す。設計書の本文は貼らず、パスを渡す。メインセッションは実装コードを書かない。

実装者は、Herdr の中で動いているとき（`dev-relay doctor` の `tool.herdr.inside=yes`）は hc の子エージェントとして起動し、それ以外では Agent ツール（`dev-relay:implementer`）で起動する。手順は `references/runtime.md` の3節。

- 変更の中心が難所（並行処理、込み入った状態遷移、性能が要件になっている箇所）だと設計書の時点で判断したとき、または実装者が同じ箇所を2回差し戻されても直せなかったときは、難所用の実装者を使う（Agent ツールでは `dev-relay:implementer-hard`、hc の子エージェントでは `runtime.md` の3節のモデルの指定）。
- 設計書に書いていない判断を実装者に任せない。迷いそうな箇所が見えているなら、委譲する前に設計書に書き足す。
- 実装者が「設計書と既存コードが矛盾している」「決めてもらわないと進めない」と報告してきたら、それは正しい振る舞い。メインセッションで判断して設計書を直し、同じ実装者に続きを頼む。
- 1回の委譲は、1つの設計書に対応する1つのまとまりにする。複数の機能をまとめて渡すと、どの逸脱がどの設計項目に対応するのかを報告から追えなくなる。
- **担当ファイルが重ならない組に分けられるなら、実装者を同時に起動する。** 設計書は1本のままでよい。1体に全部を渡すと、ほかの部分はその1体が終わるまで始まらない。分けてよい条件と守ることは `references/runtime.md` の3節。分けるのは最初の実装者を起動する前で、途中からは分けない。

### 5. 検証とコードレビューを同時に進める

実装者の報告を受けたら、先にレビュアーのコードレビューを起動する。

```bash
dev-relay review code --design <設計書> --out <結果ファイル>
# ブランチ全体を PR の前に見るとき: --base main
```

**追加のレビュアー。** `references/reviewers.md` の基準を読み、当てはまるときは、`--extra` を付けた2本目を同時に起動する（例は `references/runtime.md` の2節）。どれにも当たらなければ1本にする。使ったレビュアーと、追加した理由は、報告に書く。

レビューが動いている間に、メインセッションは次を確かめる。実装者の報告は確認の代わりにならない。

- テストコマンドを自分で実行し、結果を見る。
- 差分を自分で読む。報告された変更ファイルの一覧と `git status` が一致しているか。
- 設計書からの逸脱や、実装者が迷った点が報告されているか。あれば設計書に追記する。

### 6. 採否を決めて直す

`references/triage.md` に従う。採用候補の指摘は、実装者に差し戻す。実装者はまず指摘の再現方法を実行し、再現したものだけを、失敗するテストを残したうえで直す。再現しなかった指摘は直さない。

### 7. 報告する

`references/triage.md` の報告形式で、指摘ごとの採否と、メインセッションが自分で実行した確認の結果を書く。コミットと PR の作成は、ユーザーの指示を受けてからメインセッションが行う。PR は `/dev-relay:pr-open` の手順で作る。コミットの単位とメッセージはユーザーが決めるものだから。

コミットが済んだら、`dev-relay work done <topic>` で作業のフォルダを `.dev-relay/done/` に移す。消さないので、あとで設計書やレビューの結果を読み返せる。PR がマージされたら、PR のファイル（`.dev-relay/pr/<name>/`）も `dev-relay work done pr/<name>` で移す。

## bugfix モード

不具合の修正では、設計書の代わりに原因メモを書く。出荷する変更は、実行して得た証拠で説明できるものだけにする。

1. **再現する。** メインセッションが自分で不具合を再現する。再現しないときは、条件を絞る、ログを足す、入力を作る、のいずれかで再現するまで進める。推測のまま直さない。
2. **原因メモを書く。** `<work.dir>/cause.md` に、症状 / 再現手順（コマンドと出力）/ 原因 / 直し方 / テスト方針 を書く。原因は、症状が見えた場所ではなく、システムが最初に誤った動作をした場所まで遡って書く。ガード、リトライ、握りつぶしで症状だけを消す直し方は、その状態が正当に起こりうる場合に限る。
3. **実装を委譲する。** 原因メモを設計書として渡す。実装者は、失敗するテストを先に書き、失敗を確かめてから直す。
4. **検証とコードレビュー。** full モードの5と同じ。`--design` に原因メモを渡す。メインセッションは、手順1の再現手順をもう一度実行し、直ったことを確かめる。単体テストが通ることは、不具合が無いことの証明にならない。
5. **採否を決めて報告する。** full モードの6・7と同じ。報告には、修正前の失敗と修正後の成功の出力を両方載せる。

設計レビューは省く。原因が複数のモジュールにまたがり、設計の変更が要ると分かったら、full モードに切り替える。

## review モード

設計書は書かない。最初に言い直した目的を `--intent` で渡す。

```bash
dev-relay review code --intent "<変更の目的>" --out <結果ファイル>
```

レビューを起動したあとは、full モードの5〜7と同じ。修正が小さければ、実装者に差し戻さずにメインセッションが直してよい。その場合も、指摘が再現することは自分で確かめる。

## 作業の原則

実装者にも同じ原則を渡している（`references/implementer-prompt.md`）。メインセッションも設計と確認で同じ基準を使う。

- **最小の差分にする。** 問題を解決する最小の変更を選ぶ。同じ判断を複数の場所に書かない。
- **足す前に消す。** 不要になるものを先に消し、単純になった土台の上に作る。
- **原因を直す。** まず再現する。症状が出た場所ではなく、最初に誤った場所を直す。
- **テストは振る舞いを確かめる。** 利用者から見える結果を検証する。実装を壊せば落ち、内部だけを変えたときは通り続けるテストにする。
- **実物で確かめる。** 完了と言う前に、実際に動かして結果を見る。「コンパイルが通った」や実装者の自己申告は確認ではない。確認はコマンドとして残し、あとで再実行できるようにする。

この5つは、cursor/plugins の pstack（MIT ライセンス）の原則集を元にしている。

## 守ること

- **レビュアーは読み取り専用で動かす。** レビュアーが作業ツリーを変更すると、実装者との同時編集で衝突する。読み取り専用の強さはレビュアーで違う（詳細は `references/reviewers.md`）。
- **別ベンダーに送る内容を確かめる。** 差分と設計書は、選ばれたレビュアーの提供元に送られる。`.env`、秘密鍵、顧客データが混ざっていないかを依頼の前に確かめる。スクリプトはファイル名から疑わしいものを警告するが、止めはしないし、ファイル名しか見ていない。`--dry-run` を付けると、送る予定の内容だけを出力して終わる。
- **実装者はコミットしない。** レビュー前の差分を履歴に残さないため。
- **再レビューは1回まで。** それでも残る論点は方針の選択なので、ユーザーに決めてもらう。
- **自分の設計を自分だけで承認しない。設計したモデルが自分で実装しない。** full モードで担当を分けている理由そのものなので、急いでいても省かない。省きたいときは、モードを変えることをユーザーに提案する。
