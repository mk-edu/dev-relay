# dev-relay

設計・実装・レビューを別々のモデルに分担させる Claude Code プラグイン。

同じモデルが書いたものを同じモデルが確かめると、同じ前提と同じ見落としが残る。そこで、設計はメインセッション、実装は Claude Code のサブエージェント、レビューは別ベンダーのモデルが受け持つ。レビューの指摘は再現できたものだけ採用する。

## インストール

```
/plugin marketplace add mk-edu/dev-relay
/plugin install dev-relay@dev-relay
/dev-relay:setup
```

`/dev-relay:setup` は道具の状態を調べ、コードを送ってよい提供元と、追加のレビュアーを使うかを選択式で決める。

必要なのは Claude Code だけで、macOS と Linux に対応している。Codex CLI、Cursor CLI と `jq`、Herdr は任意で、どれも無くても Claude の別モデルがレビュアーになり、同じ手順が最後まで進む。PR のコマンドには GitHub CLI（`gh`）が要る。

## 使い方

### 開発

`/dev-relay:dev` を使う。モードは3つ。

| モード | 使う場面 | 進め方 |
|---|---|---|
| `full` | 機能追加や複数ファイルの変更 | 設計書 → 設計レビュー → 実装 → コードレビュー |
| `bugfix` | 不具合の修正 | 再現 → 原因メモ → 失敗するテスト → 修正 → コードレビュー |
| `review` | すでにある差分 | コードレビューだけ |

例: 「検索結果にページ送りを足したい。full で進めて」

### PR

| コマンド | すること | 頼み方の例 |
|---|---|---|
| `/dev-relay:pr-open` | 今のブランチの変更から PR を作る | 「この変更で PR を作って」 |
| `/dev-relay:pr-respond` | 自分の PR に付いたレビューと CI の失敗に対応する | 「レビューのコメントに対応して」 |
| `/dev-relay:pr-review` | 届いた PR をレビューし、再現した指摘だけをコメントする | 「PR #12 をレビューして」 |
| `/dev-relay:pr-watch` | 自分へのレビュー依頼と、自分の PR の状態を一覧にする | 「レビュー依頼が来ていないか見て」 |

GitHub に書く前に、宛先と下書きを見せて承認を待つ。対象は `github.com` のリポジトリだけで、フォークからの PR は作らず、レビューもしない。同じ PR に対して、複数のセッションから同時には動かさない。`pr-watch` を定期的に動かしたいときは `/loop` と組み合わせる。

### 作業のファイル

設計書、レビューの結果、PR の下書きなどは、リポジトリの `.dev-relay/` に置かれる。中身はすべて git に無視される。

```
.dev-relay/
├─ <topic>/       1件の作業（design.md と review/、impl/、logs/）
├─ pr/<branch>/   PR の下書き、届いたレビュー、CI のログ
├─ pr-review/     対応待ちの一覧（inbox.md）と、届いた PR のレビュー
└─ done/          終わった作業
```

作業がコミットされると、そのフォルダは `dev-relay work done <topic>` で `done/` に移る。`done/` は要らなくなったら自分で消してよい。

## レビュアーの選ばれ方

候補のレビュアーのうち、使えるものを上から選ぶ。次の表は、コードの送り先がすべて許可されている場合の例。

| 環境 | 設計・コードレビュー | 追加のレビュアー |
|---|---|---|
| Codex あり、Cursor あり | Codex | 設定が `auto` なら Cursor 経由のモデル、`off` なら Claude |
| Codex あり、Cursor なし | Codex | Claude |
| Codex なし、Cursor あり | Cursor 経由のモデル | 設定が `auto` なら Cursor 経由の別のモデル、`off` なら Claude |
| どちらもなし | Claude | なし |

許可が無ければ、どの環境でも Claude になる。Claude で代替したときは独立性が落ち、報告にその旨が書かれる。

## 設定と見直し

| コマンド | できること |
|---|---|
| `dev-relay doctor` | 今どのレビュアーが選ばれるか、何が飛ばされたかが分かる |
| `dev-relay config vendors` | コードを送ってよい提供元を見て、変える。リポジトリごとの設定が利用者の既定より優先する |
| `dev-relay config metered` | 追加のレビュアーを使うかを見て、変える |
| `dev-relay config role` | 役割ごとの候補を手元の設定として上書きできる |
| `/dev-relay:refresh` | レビュアーの割り当てを見直せる |
| `dev-relay smoke` | 本物のレビュアーを作り物の差分に対して動かし、出力形式を確かめる |

設定はプラグインの外に保存され、プラグインを更新しても消えない。

CLI の更新やモデルの入れ替わりで、レビュアーの割り当てが古くなったり動かなくなったりすることがある。CLI のバージョンが変わったときや、前回の確認から30日たったときなどは、セッションの開始時に1行で知らせる。`/dev-relay:refresh` は前回の確認からの変化を一覧にして割り当ての変更案を出し、承認した変更だけを手元の設定に書く。通知そのものを止めるときは `dev-relay config notice off`。

## 外部への送信と自動の操作

差分と設計書は、選ばれたレビュアーの提供元（OpenAI、Cursor とその先のモデル提供元）に送られる。送り先は `setup` で選んだものだけで、入れただけでは外部に送らない。`--dry-run` を付けると、送る内容だけを出力して終わる。

追加のレビュアーは、利用者自身の契約によっては、利用量に応じた料金がかかることがある。既定では無効で、`setup` で有効にしたときだけ使われる。`dev-relay smoke` でも作り物の差分が許可された提供元に送られ、`metered` が `auto` のときは課金されうる候補も動く。

| 扱い | 操作 |
|---|---|
| 自動で行う | レビューとテストの実行、セッション開始時の CLI のバージョンの確認（ネットワークは使わない）、設定フォルダへの確認の記録 |
| 指示か承認のあとに行う | コミット、push、PR の作成、返信とレビューの投稿、CI の再実行 |
| 行わない | マージ、force-push、PR の承認と変更の要求、スレッドの解決、他人のコメントの編集 |

PR は `gh` で有効なアカウントの名義で作られる。`setup` は、利用者が選んだときだけ Herdr（`hc`）のインストーラを実行する。それ以外の道具は入れない。
